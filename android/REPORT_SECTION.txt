ANDROID APPLICATION - ARCHITECTURE (copy into the Word report)

The native Android application (CHOMS) was built in Android Studio using Java and follows the Model-View-ViewModel (MVVM) pattern combined with the Repository pattern. The View layer consists of Activities and XML layouts (sign in, create account, dashboard, beneficiaries, visits, referrals, appointments, reports and administrator user management). They only display data and forward user actions. Each screen has a ViewModel (AuthViewModel, BeneficiaryViewModel, VisitViewModel, ReferralViewModel, AppointmentViewModel, DashboardViewModel, ApprovalsViewModel) that validates form input, holds the screen state in LiveData and survives screen rotation. The Model layer contains plain Java classes (User, Beneficiary, Visit, Referral, Appointment) that mirror the Firestore documents.

All data access is isolated in the Repository layer (AuthRepository, UserRepository, BeneficiaryRepository, VisitRepository, ReferralRepository, AppointmentRepository, DashboardRepository). ViewModels never call Firebase directly. The repositories apply role-based access control: a user (approved health worker) only queries records where chwId or assignedChwId equals their own user ID, while administrators query the whole collection. Validation (South African ID Luhn check, phone normalisation, strong passwords, mandatory consent, date and time rules) and friendly error messages for failed sign-in, duplicate accounts, empty fields and network or permission failures are implemented in the util package and covered by JUnit tests.

Users create their own accounts in the app (Firebase Authentication email/password). Registration writes a locked profile to users/{uid} with role "pending"; the Firestore rules only allow this exact shape for self sign-up, so nobody can register as a user or administrator. An administrator approves the account (role "user") and can edit a person's name, phone and role, or delete the account, from the Users screen (or the web app). Deleting calls the deleteUser Cloud Function, because only a trusted server can remove another person's Firebase Authentication login. The Android app connects to the same Firebase project as the web application and the website, using identical collection and field names, so data captured on a phone appears in the web dashboard and the reverse. Security is enforced on the server by the Firestore rules. Every operation (register, approve, create, update, delete) is committed in one batch together with its entry in the append-only audit log, and the rules reject any change that arrives without its log entry.
